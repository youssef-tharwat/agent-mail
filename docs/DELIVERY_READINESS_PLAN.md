# Reliable default delivery and observed readiness

Status: implemented and validated for v0.8.0. This is a product contract,
not an AWP-specific repair. Herdr and Fleet remain optional.

## Required behavior

1. Managed Codex/Claude launches establish a local delivery worker automatically,
   verify that its authenticated stream responds, and attach their native wake path.
   If the worker cannot start, fail the managed launch with a concrete error.
2. Registration, hook configuration, socket writes and queue acceptance never mean
   an agent has received a notification. Setup reports verification pending until
   the agent explicitly acknowledges a challenge sent over its actual wake path.
3. Sending and task decisions remain durable when a recipient is offline. Their
   results separately report persistence and each affected recipient's delivery
   readiness. Unavailable/unverified delivery is visible immediately, including
   a corrective action; it cannot masquerade as delivered mail.
4. All evidence is scoped to group, registration generation, launch/session and
   endpoint identity. Replacement, relaunch or endpoint recreation invalidates it.
5. No acknowledgment resolves mail, accepts a task or changes workflow authority.

## Evidence, not inferred cognition

Keep these distinct: configured route; transport accepted; matching runtime receipt;
agent acknowledged. Only the last confirms that the agent acted on the delivered
challenge. It does not prove understanding, task progress or future availability.
An absent acknowledgment is failed/unverified readiness, not proof of disobedience.
Do not describe hook execution alone as model consumption.

The challenge is small and generated by Mail, with an opaque nonce. Only the target
agent's authenticated CLI acknowledgment for the current connection can satisfy it.
The nonce appears only in the dispatched probe, never in ordinary status/context or
an operator's verification response. Hooks may report receipt but never acknowledge
on the model's behalf. Local operators with database access remain trusted; this is
an operational check, not attestation against a malicious local administrator.

## Implementation sequence

- [x] Add a schema migration and typed readiness states. Store one current probe per
  agent: route identity, nonce, timestamps, bounded retry budget, receipt/ack evidence
  and latest connection health. Existing agents migrate as unverified, never ready.
- [x] Reconcile probes in the existing worker. Reuse native Codex queue, Claude inbox
  and opted-in Herdr prompt delivery; no parallel broker, scheduler or workflow engine.
  Probe idle clients only, at most three attempts per route, with a finite deadline.
  Pending probes survive worker restart. An explicit verification retry can create a
  new attempt after failure; restarting the worker cannot reset its budget.
- [x] Match Claude's notification ID at its native hook boundary and inject the
  acknowledgment instruction there. Codex receives it through the real native queue.
  Herdr submits it only with its existing explicit prompt-policy consent.

  Claude hook context, and skip a standalone probe while that wake is pending.
  Keep standalone checks for agents with no pending notification. Explicit nonce
  acknowledgment remains required for both paths. The challenge uses the sending
  binary's absolute path so agent shells with a rebuilt PATH still use the current
  schema and hidden acknowledgment command.
- [x] Automatically establish the worker for managed launches and initiate checks
  when a supported route appears. Custom commands stay explicitly unsupported for
  idle delivery. Do not silently opt into unguarded Herdr prompts or remote relay.
- [x] Add explicit `agent retry NAME` and target-authenticated `agent ack NONCE`.
  Ordinary agents receive the acknowledgment instruction from the probe itself;
  they do not poll, remember a checklist or maintain readiness flags.
- [x] Add readiness to agent/status/diagnostic output and outgoing mutation results.
  Preserve successful writes even if diagnostics fail, with readiness unknown and
  an explicit diagnostic error. Filter every report to its authorized group.
- [x] Update README, usage and bundled skill around the default managed flow.

## Failure and lifecycle rules

A verified check is historical evidence, not eternal liveness. Current readiness also
requires a running worker, enabled policy, a current healthy route and a registered
agent. Paused, notification-only, missing, stale, expired and unreachable states are
explicit. Acknowledgments from another group/agent, an old route or an expired probe
are rejected; repeating an accepted acknowledgment is idempotent for that route.

Do not clear a pause, replace a binding, start an unrelated agent, kill a client,
retry a tool call or automatically mark business work finished. Failed verification
stays visible with its reason. No reminder storm: one bounded probe cycle per route,
not one per message or turn. Reuse existing state/log paths and worker locks.

## Verification gates

- Fresh native setup without a manually started service.
- Simultaneous managed launches: one worker, no stolen stream socket.
- Codex and Claude: idle notification → agent CLI acknowledgment → ready.
- Queue accepted but ignored: never ready. Claude matching hook alone: never ready.
- Stopped service, missing endpoint, disabled policy, blocked/active client and timeout.
- Lost receipts, duplicate acknowledgments, worker restart and exhausted budgets.
- Rebind, retire/restore, endpoint replacement, new launch and cross-group nonce use.
- Sending/replying and task assignment/update while unavailable: committed once,
  unambiguous readiness output, no loss or false delivery claim.
- Existing task/mail/stream/recovery tests and strict Clippy remain green.
- Real-client acceptance must be reported separately from simulated protocol tests.
  If native permissions prevent the check, report that limitation; never manufacture
  an acknowledgment or bypass the client's approval policy to claim success.

No ACP, cloud account, hosted broker, workflow replay or cross-group messaging.


## Validation evidence — 2026-09-30

Validation: **94 tests (including one doctest) passed**, strict Clippy over all
targets/features passed, and formatting/diff whitespace checks passed.

Automated checks exercise the real CLI and disposable stores, with simulated
native/Herdr endpoints. They cover concurrent automatic worker startup, exact
Codex queue challenges, Claude inbox/hook receipt versus explicit acknowledgment,
Herdr plugin/policy enforcement, wrong-agent/group nonces, registration replacement,
new-launch invalidation, stale health (including a dead Claude listener with its socket file remaining),
missing endpoints, expiry, lost receipts,
durable retry budgets, duplicate acknowledgments and explicit restart. Mutation
checks cover send/reply, task creation/reassignment and idempotent retries while
recipients are unavailable. Closed-pool fault injection returns unknown readiness
instead of turning a committed write into a failure.

The supplied AWP v0.7.0 report is separate, user-observed production evidence:
message 49 eventually woke L18 on a scheduled retry and L18 replied. The initial
60-second idle observation was insufficient. The new status exposes retry timing
and requires the exact probe acknowledgment; unrelated pane activity cannot pass.

A live Codex acceptance used a disposable store and confirmed that a normal
notification carried the same-binary challenge, the agent acknowledged it, and
status --check reported ready while the session was connected. The agent left the
task open and could not change it as a non-writer. Claude live acceptance was not
run because the installed CLI was unauthenticated; automated bridge and inbox tests
passed. Existing live stores and installed v0.7.0 were not migrated or replaced.

Historical v0.8 limitation: unresolved old obligations could exhaust the per-agent
wake budget, and status --check did not expose the legacy counter. The event-scoped
Herdr wake follow-up automatically rearms new actionable generations, records
visible retrieval independently from resolution, and exposes current generation
exhaustion through attention and the `herdr_wake` diagnostic. `alerted=1` does not
block delivery attempts, including for an interactive `done` Herdr agent.

The full operating guide now lives in `docs/agent-guide.md` and remains embedded
in `agent-mail --skill`. `skills/agent-mail/SKILL.md` is a small loader distributed
through skills.sh. It loads the installed binary's guide on invocation, so a binary
upgrade supplies matching operating instructions without updating copied references.
skills.sh owns installation and loader updates (`npx skills update agent-mail -g`);
Agent Mail does not maintain a separate installer or modify installed skill files.
Active conversation context is unchanged until the guide is loaded again.
